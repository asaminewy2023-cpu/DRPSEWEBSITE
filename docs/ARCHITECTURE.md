# Architecture

## Monorepo layout

```
apps/
  cms/       Payload CMS admin + REST API (Next.js, port 3000)
  website/   Public site (Next.js, port 3001)
packages/
  ui/         Shared UI: language/accessibility contexts, locales, getT,
              Header/Footer/LangSwitcher/AccessibilityToolbar chrome (@sevp/ui)
  shared/     Shared types + CMS HTTP client (ports to @sevp/shared)
  config/     Shared TS config
docs/        Project & phase docs
docker/      compose, nginx, Dockerfiles
scripts/     One-off and dev scripts
```

## Data flow

- **CMS (`apps/cms`)** owns all content. Payload manages the Postgres schema via
  `migrations/` and exposes `/admin` and `/api/*`. Admin/users/auth live here.
- **Website (`apps/website`)** is presentation-only. It reads content through the
  CMS REST API (`@sevp/shared` client) and never touches Postgres directly.
- **Shared types** (`packages/shared/src/payload-types.ts`) are generated by the
  CMS (`payload generate:types`) and imported by the website — one source of
  truth for every collection's shape.

## Shared packages

- `@sevp/shared` (`packages/shared`) — `cmsFetch` / `cmsQuery` / `cmsList`
  HTTP client plus generated Payload types.
- `@sevp/ui` (`packages/ui`) — client chrome and contexts. The server-only
  `getT()` lives behind the `@sevp/ui/server` subpath export so client
  components never pull `next/headers` into the bundle. Tailwind scans the
  package via `@source` in the website's `globals.css`, and both packages are
  listed in the website's Next `transpilePackages`.

## CMS content model

- `apps/cms/blocks/` — Gutenberg-style block definitions shared across
  collections: `paragraph` (rich text), `heading`, `hero`, `image`, `list`,
  `quote`, `cta`.
- Dynamic collections (`posts`, `announcements`) carry both a `content`
  rich-text field and an optional `blocks` field. When `blocks` is non-empty it
  is the preferred body (the site renders blocks over rich text).
- `programs` and `shorts` have an optional `blocks` field too.
- Static routes are editable through the `pages` collection (group "Site"): each
  doc has `slug` (matches the route, e.g. `about`), a hero group, `metaDescription`,
  a `blocks` field, and `published`.

## Website block rendering

- `apps/website/src/lib/cms-data.ts` — `getPage(slug)` / `getPages()` fetch the
  `pages` collection (published only) through the shared `cmsList` helper.
- `apps/website/src/components/BlocksRenderer.tsx` — maps block JSON to JSX for
  every `blockType` (`paragraph`, `heading`, `hero`, `image`, `list`, `quote`,
  `cta`). `paragraph` blocks reuse the custom Lexical renderer in `RichText.tsx`.
- `apps/website/src/components/CmsPage.tsx` — async server component. Given a
  `slug` + `fallback` it renders the CMS page (hero + blocks) when a published
  doc exists, otherwise returns the hardcoded fallback UI.
- Dynamic detail pages (`blog/[slug]`, `announcements/[id]`) render `blocks` over
  `content` rich text when non-empty.
- Editorial static routes (`about`, `cluster`, `documents`, `projects`,
  `public-services`) call `CmsPage({ slug, fallback })` and are therefore
  CMS-editable with a hardcoded fallback.
- Because an async server component's return type is `Promise<Element>`, pages
  invoke it as `return CmsPage({ ... })` rather than `<CmsPage />` — React's JSX
  types don't accept promise-returning components in element position.

## CMS app structure

The CMS admin lives under `apps/cms/app/(payload)/` (Next.js route group):

- `layout.tsx` — mounts `RootLayout` with `handleServerFunctions`; **this is
  required**. Without it the admin UI crashes with
  `useServerFunctions must be used within a ServerFunctionsProvider`.
- `admin/[[...segments]]/` + `importMap.js` — generated Payload admin routes.
- `api/[...slug]/route.ts` — generated REST handlers.

The runtime crash `Cannot destructure property 'config' ... is undefined`
(payloadcms/payload#17095 — `ConfigSync` reads `use(ConfigContext)` with no
provider) is fixed via a `patchedDependencies` entry for `@payloadcms/ui` in the
root `pnpm-lock.yaml`. Reinstall (`pnpm i`) reapplies it automatically.

## Environment

- `apps/cms/.env` — `DATABASE_URL`, `PAYLOAD_SECRET`
- `apps/website/.env` — `CMS_BASE_URL` (server fetch) and
  `NEXT_PUBLIC_CMS_BASE_URL` (client links to admin), defaulting to
  `http://localhost:3000`.
- In `docker/`, `docker-compose.yml` injects these per-service.

## Ports (dev)

- CMS: `http://localhost:3000` (admin at `/admin`, API at `/api`)
- Website: `http://localhost:3001`
- The apps run separately (`pnpm dev:cms`, `pnpm dev:website`).
- `pnpm dev` runs both via `concurrently`.

## Database

- Payload owns the `Sevp` Postgres database (tables `posts`, `announcements`,
  `programs`, `gallery_items`, `shorts`, `users`, `contact_messages`, …).
- Legacy Prisma tables may still coexist from the pre-migration era. They are
  unused; see Phase 4 of `docs/STEPS.md` to drop them.

## Tooling

- `pnpm` workspaces (`pnpm-workspace.yaml`) with `apps/*` and `packages/*`.
- `packages/config/tsconfig.base.json` shared by all workspaces.
- The CMS `next.config.ts` is wrapped with `withPayload`; the website only sets
  `transpilePackages` + image/header config.
